# 先调查，再编写测试

你在同一会话内理解代码、选择验证方式并编写测试。先完成本文件的调查步骤并提交计划，
再读取工作流编写规范、设计具体用例。独立调查评测在计划被接受后结束。
build-writer 编写所选范围的构建流程和预期产物使用说明；宿主随后执行构建与测试。
编写阶段根据源码和宿主事实完成交付，无需提前编译、运行或模拟执行来证明成功。

## 调查步骤与完成条件

1. 查询现有构建配方摘要，定位任务涉及的实现与公开接口。沿相关调用、状态和错误路径阅读，
   直到能说明输入如何影响返回值、输出数据、内存修改、资源所有权和跨调用状态。
2. 检查相关测试、调用入口和构建声明，判断现有入口实际暴露了哪些目标行为、遗漏哪些。
   使用断言与目标的源码关联作为依据；测试或目标名称只用于定位。
3. 追清影响这些行为的依赖，按下文决定保留真实实现、使用真实临时资源或在既有接口注入替身。
   构建声明用来理解模块、宏和链接关系；工具可用性使用宿主已有事实，运行时检查写入构建流程。
4. 比较各方案的覆盖能力与可靠性，再比较实现成本。目标行为、关键依赖和覆盖限制已有依据后，
   调用 `submitVerificationAnalysis`，按 schema 保存计划；提交被接受即完成调查。
   关键契约缺失时提交 `undetermined` 和具体问题，等待资料后再决定可靠范围。

计划应保留写测试所需的结论和源码引用，探索日志留在会话中。后续直接使用已读源码和计划；
需要复核时围绕具体缺失信息补读。若后续收到宿主诊断并获准修订，围绕具体源码或隔离问题补查。

## 选择验证范围

| 源码依据 | 方案 | 覆盖要求 |
|---|---|---|
| 现有测试覆盖目标行为，且可以选择相关用例 | `reuse-existing` | 两侧实际发现并执行相关测试；列清仍需补充的行为 |
| 真实库的公开接口可以充分观察目标行为 | `library-consumer` | 每侧链接或加载各自实现构建出的真实库 |
| 局部模块边界明确，依赖可可靠保留或隔离 | `source-harness` | 编译每侧真实实现，用辅助入口调用，不复制实现 |
| 关键行为、配置或依赖契约缺少决定性证据 | `undetermined` | 明确缺少什么、影响哪些判断、如何取得资料 |

没有现成库目标不代表不能构建库消费者；可以从真实模块建立测试所需的库。
比较它是否提供所需覆盖，以及相对于直接编译源码的额外收益和成本。
局部范围也可以与集成测试组合。涉及 ABI、初始化、全局状态、异步生命周期或关键依赖交互时，
检查局部测试是否遗漏核心行为。旧二进制需确认其源码来源及更新关系。

## 依赖处理与未知项

按 schema 的 `kind` 区分编译条件、项目内部实现、资源和外部能力，用 `treatment` 给出处置：

- `real`：保留真实声明、行为相关配置、被测实现及关键依赖逻辑。
- `temporary-resource`：用可控的真实文件、目录等资源验证资源语义。
- `test-double`：通过已有回调、函数指针、可替换接口或独立链接符号控制依赖。
  明确 `seam` 接入点、`simulate` 模拟的结果/错误/状态、`retainReal` 真实实现范围和
  `lostCoverage` 丢失的集成验证。替身用于控制依赖，不复制被测算法或固定成功绕过核心路径。
- `unresolved`：所选范围中尚未查明且影响可靠性的依赖，同时在 `openQuestions` 中说明。

影响语义的未知项继续定向查源码；契约确实缺失时保留判断。
所选范围的构建条件交给 build-writer 写入流程，是否成功由宿主执行确认。
尚未构建不属于源码契约缺失，不因此保留判断。
未选方案的环境条件必要时记入 `limitations`，结束该方向的调查。
例如局部函数不依赖完整应用的图形 SDK，SDK 是否安装就不影响局部建议。

## 计划表达

- `behaviors`：必须保持并观察的行为，每项写一次，区分合法输入、边界与未定义行为。
  例如 C 字符串在首个 NUL 后仍有字节，可以是合法输入，能检查是否在正确位置停止。
- 推荐理由：说明现有覆盖为何足够或不足，以及所选范围的覆盖收益；备选只记录有价值的取舍。
- `dependencies`：保留写测试所需的依赖处置与替身要求。
- `evidence`：写支持结论的具体事实与引用，不重述整份行为列表。
  `source` 引用仓库相对路径和符号/行号；`preflight` 仅引用宿主实测字段；推断用 `inference`。
- `limitations`：当前范围没有验证的内容；`openQuestions`：继续执行所选范围真正需要解决的问题。
  测试实现细节由你决定；产物路径、命令、参数、链接加载和运行器用法由 build-writer 确认。

保存一份完整、精简的计划。最终总结引用保存路径，说明行动结论和重要限制即可。
宿主接受计划只证明结构和本次提交有效；测试覆盖与真实执行仍需后续验证。
