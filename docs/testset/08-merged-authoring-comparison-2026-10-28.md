# 调查与测试编写合并：真实运行对比（2026-10-28）

本次已把源码调查与测试编写放入同一个模型会话，保留独立的构建角色。实际运行证明新流程能完成局部函数的测试编写与双侧验证，但没有获得提速：当日旧版编写会话为 294 秒，合并后两轮为 441 秒和 355 秒。覆盖有所增加，也有遗漏，不能说合并后质量全面提高。

旧版先保存为本地提交 `7248fc4`，再运行旧版对照、修改实现并运行合并版。本次未推送、创建 PR 或合并远端分支。

## 实现与提示词变化

旧流程是测试编写会话先调用调查子角色，接收报告后再读代码、写测试，并向构建子角色请求构建。新流程由测试编写会话直接调查源码、提交计划，接着用同一段上下文设计用例和辅助程序，再请求构建子角色。

- 删除生产 `verification-scout` 子角色及对应 skill；新增共用的 `verificationPlanningPrompt` 和 `verification-planning` skill。
- 调查指导要求先确认行为、现有覆盖和关键依赖，再选择复用现有测试、调用真实库或直接编译局部真实源码。没有现成库目标，也可以从真实模块构建测试所需的库。
- 影响当前方案的未知项才继续调查。完整应用所需、当前局部方案不用的 SDK 不应阻塞局部测试，也不应据此继续寻找宿主安装位置。
- 计划保存后再读取工作流实现规范；后续复用已读源码，只围绕具体缺失信息补查。行为列表、推荐理由和证据分别写清，避免同一内容反复展开。
- 测试编写会话负责用例、观测和辅助代码；构建角色负责实测编译链接、环境问题、产物路径及使用说明。辅助材料仍由宿主固定，并以相同字节交给两个 worktree；每侧构建各自的真实实现。
- 保留本次计划提交检查、依赖声明、测试文件检查、双侧执行与最终判定机制。计划获宿主接受只证明结构有效，不证明建议正确或测试通过。

独立调查评测复用生产调查指导，在提交计划后结束。旧 `scout` CLI、场景 ID 和证据格式保留，方便使用已有场景与历史数据；生产运行没有新增模式开关。

## 比较方法与证据边界

完整编写使用 `local-function` 场景：`text_copy` 是无外部依赖的局部 C 函数，完整应用依赖 Vulkan。任务未预告应选策略或后续错误补丁。每轮真实调用一次测试编写会话，由模型调查并生成辅助程序和工作流，随后固定这套材料测试一个等价补丁和两个错误补丁。

独立调查选择三个有不同决策难点的场景：相关测试与无关冒烟测试并存、真实内部依赖加可注入分配器、当前产品配置与外部依赖契约缺失。程序核对了前后任务、源码哈希和预算一致。

- 宿主为 Windows；请求模型别名为 `sonnet`，所有会话响应均声明 `deepseek-v4.1-flash`。这不是 Claude Sonnet 能力测评。
- 没有调用真实重构模型，候选修改使用固定补丁；没有调用评分模型，独立调查结果仍是 `pending-rubric`。下文质量判断来自源码与执行记录复核，没有伪造评分。
- 比较包含结构调整和提示词调整的共同效果，不能单独归因于减少一个角色。样本为旧版一轮、合并版两轮，没有统计显著性结论。
- 生产输入在合并版运行期间保持不变。各轮受控源码未变，辅助材料与工作流哈希核对通过。
- 独立调查入口不包含完整编写上下文，也不写测试，不能用它的耗时代表完整会话。

### 执行记录说明了什么

两轮合并会话提交计划后，都没有再用 Read 重新遍读那四份项目文件，调查结论确实直接用于编写。但额外命令抵消了这一收益：

- **A 重复编译和自检较多。** 主会话自行编译辅助程序，构建子角色随后又编译；主会话还制作了多份模拟输出与错误输出自检脚本。这些检查部分有价值，但说明职责边界没有稳定执行。
- **B 仍调查无关环境。** 查询 Vulkan 环境变量和 `C:/VulkanSDK`，据变量为空和常见目录不存在推断 SDK 缺失、完整应用不能构建。该证据不足以证明整个宿主没有 SDK，也没有实际构建完整应用；它与已经选定的局部方案无关。
- **A 错分未知项。** 把局部方案不用的 Vulkan 记为 `unresolved`，第一次提交因缺少对应问题被 schema 拒绝。补写问题后接受，并不表示该 SDK 真的是局部方案的阻碍。
- **A 报告有文字矛盾。** 一项描述把 `capacity == length+1` 放入 `capacity <= length` 的括号中；实际测试的该边界实现正确。

日志不能精确拆分推理、生成和服务等待时间，因此不能把全部变慢归因于某一个命令或合并本身。

## 实际检测能力与自动汇总的局限

三轮中每套生成材料均固定复用于全部补丁，没有看到错误后补写测试。等价修改均被接受，两个预设错误均触发实际行为检查。

| 补丁 | 当日旧版 | 合并 A | 合并 B |
|---|---|---|---|
| 等价提取辅助函数 | `ACCEPTED` | `ACCEPTED` | `ACCEPTED` |
| 截断时返回复制长度 | C 检查失败，原生退出 1 | TS 工作流检查真实输出后抛错，原生退出 0 | C 检查失败，原生退出 1 |
| capacity=1 漏写 NUL | C 检查失败，原生退出 1 | TS 工作流检查真实输出后抛错，原生退出 0 | C 检查失败，原生退出 1 |

所有错误补丁的生产状态都是 **`ABORTED`**：候选测试先失败，没有进入双侧观测比较，不能改记为 `REJECTED`。

合并 A 的失败依据明确：

- 截断返回值：`len1_cap1` 实际返回 `0`，期望 `1`；目标字节为 `00`。
- 漏写结尾 NUL：`len0_cap1` 实际目标字节为 `a5`，期望 `00`。
- 两侧均构建成功，原始版本测试通过。候选原生程序正常退出 0，TS 工作流依据真实输出报告契约不一致，没有超时或 signal。

合并 B 中，截断错误触发 `c_trunc`、`d_cap1`、`k_long_trunc`；漏 NUL 触发 `d_cap1`、`h_empty_cap1`。两侧构建成功、原始版本测试通过，候选程序正常退出 1，没有超时或 signal。

当前 `scripts/e2e-verification-authoring.ts` 的 `inspect()` 仅把候选原生进程的非零退出识别为 `candidate-test-failure-review-required`。它漏掉了 A 这种“原生程序正常输出，工作流执行断言”的合法形式：

- A 原始 `summary.json` 保留 **`ok:false, complete:true`**，两个错误控制的 `detection:null`；本次没有覆盖或修改这些原始结果。
- B 原始汇总为 `ok:true`；旧版当日对照也为 `ok:true`。
- 源码与执行记录复核确认 A 检出了两个错误。这是评测汇总漏分类，生产没有把错误接受；但也不能声称自动评测全部通过。

## 覆盖的增加与遗漏

| 行为或检查 | 当日旧版 | 合并 A | 合并 B |
|---|---|---|---|
| 输入场景数 | 11 | 41 | 11 |
| 宿主观测数 | 25 | 45 | 36 |
| 零容量的 NULL / 非 NULL 目标 | 有 | 有 | 有 |
| capacity=1、截断、恰好容纳、空串 | 有 | 有 | 有 |
| 首个 NUL 后仍有非零字节 | 有 | 有 | 有 |
| 目标后部未写入区检查 | 有 | 有 | 有 |
| 目标前部哨兵 | 无 | 16 字节 | 无 |
| 显式高位字节输入 | 有，C3/A9/FF | 无 | 无 |
| 只读源材料 | 字面量、const 数组 | 字面量、const 数组 | static const 数组 |
| 空串与 capacity=1 的独立组合 | 无 | 有 | 有 |

A 的 41 项主要是多个长度与容量组合，不能当作质量提高四倍。A 增加了前部越界哨兵，两轮都增加了空串与最小容量组合，但均遗漏旧版的高位字节输入。观测数也受分组方式影响，不能直接等同于覆盖质量。

两轮均只编译固定的 `src/text_copy.c`，没有验证合法拆分源文件后是否仍能构建；没有调用 Linux/macOS。生成方案使用 `facts.host.executable_suffix`，这只是实现检查，不是其他系统的运行证据。

A 曾在工具仓库根创建 `.scratch-tc-verify/`，位于被测仓库外，随后自行清理。最终核对其已不存在，受控源码没有变化。这次运行没有证明 OS 文件隔离。

| 场景 | 当日旧版 | 合并版 | 方案变化与复核 |

### 已有测试：选择可解释，成本优势未证实

合并版正确追踪 `key_semantics → key_test → key_core → src/key.c`，排除了只返回成功的 `version_smoke`。它识别字符转换、错误优先级、错误时目标不变，以及字符分类边界等覆盖缺口。

改选新增库调用测试属于场景参考允许的替代方案，不能仅因标签不同判错。不过没有实际编写和执行这个消费者；复用现有测试再补少量用例，也可能更省成本。报告主动不测成功时 NUL 后尾部写入和非 C locale，这些排除限制了结论，不能说全部既有可观察行为都已保护。

### 分配器：依赖处理合理，一项覆盖排除缺乏依据

合并版保留真实 `frame → checksum/hex → nibble`，通过公开 `FrameMemory` 的 `ctx/alloc/release` 控制分配失败，记录请求大小、指针、调用次数，并验证错误清理、所有权转移和释放幂等。它没有建议替换核心校验或解码逻辑。

但报告主动排除精确分配大小 `payload/2+1`。该值传给外部回调，调用方可以观察，甚至按请求大小决定成功或失败。任务要求保持既有行为，没有授权忽略这一差异，因此这项排除缺乏充分依据。不能把本轮所有建议评价为正确；还未实现消费者实际做故障注入。

### 配置缺失：更稳妥，但调查仍不够收敛

合并版识别缺少 `device_options.h`、生成配置模板和当前 SDK/provider 契约；旧文档称无状态，但源码有 sequence 副作用，而且 NULL 检查前也会递增。于是提交 `undetermined`，没有自行补配置冒充当前产品。

旧版当日建议自己补头文件、分别测试宏为 0/1 的配置，虽承认局限，仍可能替代真实产品配置。合并版避免了这一风险，但多次重读，最后还询问源码已经确认的 sequence 是否应保持，耗时增加且仍有无效问题。

## 后续优先项

合并使调查结论与写测试衔接更直接，值得保留为当前实现，但尚未证明性能收益。下一步应先处理已经看到的具体问题：

1. 约束与当前方案无关的环境查询，以及主会话和构建角色的重复编译；避免继续增加角色来补偿边界不清。
2. 检查每项行为如何落实到测试，并要求对排除既有可观察行为给出任务依据，特别是回调参数、写入范围和跨调用状态。
3. 完善测试汇总对工作流内部行为断言的分类，同时保留编译失败、原始版本失败、超时、signal 等无效运行的拒绝规则。
4. 再用固定任务做小规模重复对比，并补一个真实库调用或依赖注入的完整编写场景，验证目前只看计划的建议能否落地。

以上是建议，本次没有在对比运行后继续修改生产提示词或评测分类规则。
